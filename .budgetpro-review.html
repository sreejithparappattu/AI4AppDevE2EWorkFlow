BudgetPro · 02 / Security analysis

Security analysis

No critical or high-severity exploitable defect was confirmed in the reviewed source. The following are concrete hardening gaps or conditional risks that should be addressed before handling real financial data at scale.

MEDIUM · hardeningAuthentication endpoints have no visible rate limit

Registration and login accept requests without throttling, lockout, or abuse controls. This can enable high-volume password guessing, credential stuffing, and registration abuse. No successful compromise was demonstrated.

Evidence: server/index.js:132–169. Recommendation: Add per-IP and per-account throttling, progressive backoff, monitoring/alerts, and an abuse-resistant signup flow; test shared-proxy handling to avoid unfair lockouts.

MEDIUM · conditionalCookie-authenticated mutations lack explicit CSRF/origin verification

Transaction creation relies on an automatically sent session cookie. SameSite=Lax and an allowlisted CORS origin are useful controls, but CORS is not a general CSRF defense; same-site cross-origin contexts can still matter (for example, a compromised sibling subdomain). The risk depends on domain and deployment topology.

Evidence: server/index.js:15–20, 49, 202–222. Recommendation: Validate the request Origin (and Fetch Metadata where supported) for state-changing routes; add a CSRF token if deployment needs cross-site cookies. Verify with browser-based tests.

LOW · defense-in-depthProduction response security headers are not configured here

The production Express setup serves static assets without visible Helmet/security-header middleware. No Content Security Policy, HSTS, clickjacking, or MIME-sniffing policy is established in this application code. An upstream proxy may already set some headers, so verify the deployed response before treating this as a live exposure.

Evidence: server/index.js:226–229. Recommendation: Add and configure Helmet (including a tested CSP); enforce HSTS at the HTTPS edge and check actual production headers.

LOW · conditionalSeven-day stateless sessions are not revocable server-side

Logout clears the browser cookie, but a copied JWT remains valid until expiry. HttpOnly reduces script access, and no token theft was observed; residual risk depends on a token being exposed through another compromise.

Evidence: server/index.js:60–61, 166–169. Recommendation: Shorten access-token lifetime and introduce revocation/rotation (for example, server-side sessions or a token-version check) if prompt invalidation is required.

Positive controls observed

IN PLACEPasswords are hashed with bcrypt (cost 12); raw passwords are not persisted.

IN PLACEJWT is held in an HttpOnly, SameSite=Lax cookie; Secure is enabled in production mode.

IN PLACETransaction queries are parameterized and scoped to the authenticated user ID.

IN PLACERequest payloads are validated and database constraints reinforce key invariants.

Scope limitation: This was static code review only. No live PostgreSQL instance, production headers, deployment proxy, browser CSRF test, penetration test, or independent dependency vulnerability scan was assessed for this report.

BudgetPro · 03 / Performance considerations

Performance considerations

The app is small and its current schema includes a useful per-user/date index. The largest expected scaling pressure is unbounded transaction-history retrieval—not React’s rendering of the eight visible recent rows.

1 · Full history is fetched and summarized in the browser FIRST BOTTLENECK

GET /api/transactions returns every transaction for the user, and React downloads all rows before filtering the current month and calculating totals. Only eight are displayed in recent activity, but the complete history is still transferred and retained. As accounts grow, response bytes, query execution, client memory, and initial dashboard time rise with transaction count.

Evidence: server/index.js:186–198; src/App.jsx:190–210, 235–250, 280–299.

2 · Dashboard aggregates are calculated after loading all rows

Monthly income, expenses, and category totals are computed in JavaScript after the full history is fetched. This repeats transfer and client work the database can do more selectively. The existing composite index supports user/date ordering; it does not make an unbounded history response small.

Recommendation: Add date-bounded SQL aggregate queries for monthly totals/category breakdown, and a separately paginated recent-transactions endpoint. Preserve a stable cursor such as (transaction_date, created_at, id) and the matching index.

3 · Connection demand grows with API replicas

The pg Pool uses its default per-process connection limit. Under load, each Node process/replica can open its own pool; multiplying replicas may exhaust PostgreSQL connections before CPU is saturated.

Recommendation: Configure pool max, acquisition timeout, and idle timeout from the database connection budget; monitor pool wait time and active connections. Use a pooler such as PgBouncer if deployment concurrency requires it.

4 · Synchronous schema setup is coupled to service startup

Every API process runs CREATE TABLE IF NOT EXISTS and index DDL before listening. This is manageable for a prototype, but production replicas should not race to own schema changes, and the runtime application account needs unnecessary DDL privileges if this stays in the request-serving deployment.

Recommendation: Move schema changes into versioned, single-run migrations; give the runtime DB role only required data permissions.

5 · Financial amount conversion can lose exact decimal behavior

PostgreSQL stores amounts as exact NUMERIC(12,2), but SQL casts them to float8 and React sums binary floating-point values. Rounding drift can appear across larger histories or calculations.

Recommendation: Keep aggregates in PostgreSQL NUMERIC and serialize decimal strings, or use integer minor units consistently; add tests for rounding and totals.

Recommended rollout

Now: Measure response size and p50/p95 latency with representative small and large histories; add query/connection metrics and error monitoring.

Before growth: Split summary aggregates from paginated history; bound page size and add deterministic cursor pagination. Validate query plans with EXPLAIN (ANALYZE, BUFFERS) on realistic data.

At higher concurrency: Load-test realistic read/write mixes, tune pool limits against PostgreSQL capacity, and introduce pooling/caching only when measurements justify them. Re-test tenant isolation and totals after query changes.

Conclusion: The current design is reasonable for a small application. Prioritize bounded data access and SQL-side summaries before transaction history becomes large; use measurements to determine the point where pooling, caching, or further indexing is warranted.
